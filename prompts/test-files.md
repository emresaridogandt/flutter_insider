## What Counts as a Test File

| Path | Status |
|---|---|
| `test/*_test.dart` | Test files — 12 of them, flat layout, no nesting |
| `test/wire_case.dart` | **Shared harness, not a test file.** Contains no `test()` calls of its own |
| `devops/api_surface_check/tests/test_e2e.py` | Python e2e test for release tooling — **not run by any CI job** |

All tests are Dart tests via `flutter_test`, split into **two groups** reported as separate CI
status checks:

| Group | Selected by | Files |
|---|---|---|
| unit | `--exclude-tags integration` (subtractive: the default) | the 8 files whose SUT the test constructs itself |
| integration | `@Tags(['integration'])` library annotation | the 4 facade concern files, which drive `FlutterInsider.Instance` |

The group is a **tag, not a directory** — `test/` stays flat. The decision rule lives in
`.claude/rules/unit-tests.md` §0. Reviewing a test file that drives `FlutterInsider.Instance`
without the tag is a finding, not a nitpick: it runs in the wrong group silently.

Native unit tests cover only the `FlutterInsiderUtils` helpers: JUnit + Mockito in
`android/src/test`, XCTest + OCMock in `ios/Tests`, run through FlutterDemo by the
`Android Native Tests` / `iOS Native Tests` jobs. There are no on-device tests. A native change to
`FlutterInsiderUtils` needs a native test there; for any other native-only change, note that the
Dart wire contract is unchanged instead.

CI runs the two groups through `devops/unit_tests.sh --group <unit|integration>`, plus a separate
`Coverage` job running the full suite via `devops/unit_tests.sh --with-code-coverage`
(`run-tests.yml`). Nothing runs `pytest`.

## Required Patterns

### Use the shared harness for tabular wire assertions

`test/wire_case.dart` provides `WireCase` + `registerWireCases`. Used by the commerce, lifecycle,
and queries test files. Prefer it whenever adding several methods that differ only in name/args —
a hand-rolled `setUp`/`tearDown` block duplicating it is a Medium finding.

```dart
import 'wire_case.dart';

registerWireCases([
  WireCase(
    name: 'visitHomePage (no args)',
    action: () => insider.visitHomePage(),
    wireMethod: Constants.VISIT_HOME_PAGE,
    wireArgs: <String, Object?>{},
  ),
], channel);
```

### Two mechanics that silently corrupt assertions

Both are easy to omit and neither fails loudly:

1. **Drain microtasks after the action.** The channel delivers asynchronously; without this the
   assertion runs before the call is captured, and the test passes for the wrong reason.

   ```dart
   action();
   await Future<void>.delayed(Duration.zero); // required
   expect(capturedCalls, hasLength(1));
   ```

2. **Null the handler in `tearDown`.** A leaked handler cross-contaminates `capturedCalls` between
   tests.

   ```dart
   tearDown(() {
     TestDefaultBinaryMessengerBinding.instance.defaultBinaryMessenger
         .setMockMethodCallHandler(channel, null);
   });
   ```

A new test file missing either is a **High** finding — it produces a test that cannot fail.

### Assert against `Constants.*`, never literals

```dart
// ❌ passes even if the constant is renamed — defeats the whole point
expect(call.method, equals('setName'));

// ✅
expect(call.method, equals(Constants.SET_NAME));
```

This is the rule that makes the test suite a real guard on the wire contract. Treat a hardcoded
method-name string in a test as a **High** finding.

### Assert the full argument map

`expect(call.arguments, isA<Map>())` alone is too weak. Assert the exact map, so an added or
renamed key is caught:

```dart
expect(
  Map<String, dynamic>.from(call.arguments as Map),
  equals(<String, dynamic>{'key': Constants.SET_NAME, 'value': 'Alice'}),
);
```

## What to Enforce vs. Ignore

### Enforce a test for

- Any new or changed public Dart method that reaches the channel → wire-contract test
- Any new `Constants.*` entry → a test referencing the constant
- Serialization logic (`serializeCustomParameters`, `getDateForParsing`, builders)
- Model/enum parsing from native payloads — cover every value **and** the unknown/fallback branch
- Bug fixes → a regression test reproducing the original failure

### Do not request tests for

- `devops/**` — release automation, exempt per `prompts/test-coverage.md`
- Native-only changes under `android/` or `ios/` outside `FlutterInsiderUtils` — no test layer covers them
- Version bumps in `pubspec.yaml`, `android/build.gradle`, `ios/flutter_insider.podspec`, `CHANGELOG.md`
- `lib/enum/*.dart` constant-holder classes with no logic
- Deletion-only diffs
- Doc-only, comment-only, or formatting-only diffs

## Test Quality Signals

Flag tests that:

- Assert only that a call happened, without checking method name **and** arguments
- Use `expect(..., isNotNull)` where an exact value is knowable
- Share mutable state across `test()` bodies without resetting it in `setUp`
- Are named for the implementation rather than the behaviour (`test('calls invokeMethod')` →
  prefer `test('setName sends method "setName" with raw string value')`)
- Add a `group` that duplicates an existing one in the same file

There are no mock factories or fixture directories in this repo — test data is built inline. A PR
introducing a mocking framework is an architectural change and needs justification.
